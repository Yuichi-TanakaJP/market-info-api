# Resource usage and free tiers

Last checked: 2026-05-23 JST

This document records the runtime free-tier limits used by `market-info-api` and the current resource-size estimate.
Use it as the capacity checklist before adding API-side cache, range/search endpoints, or new R2 publish artifacts.
Separate confirmed measurements from estimates; do not treat estimates as billing records.

## How to use this document

Before adding a new endpoint, cache layer, or publish artifact, answer these questions in the related issue / PR:

| Question | Why it matters | Where to record the answer |
|---|---|---|
| Is the response full payload, compact index, or filtered search result? | Full payloads scale with source files; compact/search responses can reduce client transfer. | API contract / endpoint docstring |
| Which R2 objects are read per request? | Determines cold-cache R2 Class B operations. | API contract and implementation notes |
| What is the source window limit? | Prevents large fan-out and large in-memory cache entries. | Query validation and docs |
| What fields are kept in API-side cache? | Determines memory pressure and whether UI has enough data. | This document or endpoint-specific docs |
| What is the measured serialized size from `MARKET_OUT_ROOT`? | Gives a repeatable baseline before Cloud Run deployment. | This document when materially changed |
| Is the cache byte-bounded or entry-count-bounded? | `TTLCache(maxsize=...)` currently limits entries, not bytes. | Cache implementation notes |
| Does R2 publish need a new compact artifact? | API-side aggregation may be too heavy for broad searches. | `market_info` publish contract / proposal |
| Which provider metrics must be checked after rollout? | Confirms estimates against billing/runtime reality. | `To verify` section and PR follow-up |

Design rule of thumb:

| Use case | Preferred shape | Reason |
|---|---|---|
| Short period data inspection | `/range` full payload with a small source limit | Preserves original payload shape; simple but heavier |
| Broad search with selective query | compact `/search` endpoint | Reduces client response size and repeated R2 reads |
| Broad search with many repeated users/queries | pre-published compact index in R2, then API cache | Avoids rebuilding large indexes in Cloud Run |
| Historical multi-year analysis | dedicated monthly/yearly compact artifacts | Keeps request fan-out and process memory bounded |

Do not increase a range/search limit only because a UI needs a wider period.
First measure the source data size, estimate API memory, and decide whether the better answer is a compact R2 artifact published by `market_info`.

Important: these are serialized JSON sizes.
In Cloud Run, cached payloads are Python `dict` / `list` objects, so process memory can be materially larger than the serialized JSON size.
The current cache is entry-count bounded (`TTLCache(maxsize=...)`), not byte-size bounded.
This detailed memory-risk estimate is focused on `ranking` because `/ranking/search` is currently the broadest API-side compact index.
Other APIs are included in the storage-size measurement above, but they do not currently have the same wide search-index cache behavior.

Example search result size:

| Query | Source dates | Full JSON scanned | Compact index | Returned response |
|---|---:|---:|---:|---:|
| `code=7203` | 31 | 10,516.2 KB | 4,561.2 KB | 5.0 KB |
| `code=7203` | 77 | 25,900.6 KB | 11,230.8 KB | 14.1 KB |

Interpretation:

- `/range` reduces R2 round trips but returns full payloads.
- `/ranking/search` still needs an API-side index, but it greatly reduces response size when the query is selective.
- A broad one-year search index is not small; avoid treating annual indexes as cheap until Cloud Run memory metrics are checked.

| API call | Cold R2 reads, approximate | Notes |
|---|---:|---|

## Current cache implementation

Confirmed from `app/cache.py`:

| Cache | Max entries | TTL |
|---|---:|---:|
| manifest | 16 | 6h |
| day object | 128 | 24h |
| range current | 64 | 6h |
| range past | 64 | 24h |
| search index current | 128 | 6h |
| search index past | 128 | 24h |

Risk:

- `TTLCache(maxsize=...)` limits entry count, not bytes.
- A one-year ranking search index is estimated at about 52.4 MB serialized JSON before Python object overhead.
- Multiple distinct one-year search ranges in the same Cloud Run instance could pressure the 512 MiB memory limit.

### Why the current cache stores Python objects

The current implementation stores the fetched or built value directly in process-local `TTLCache`.
For JSON responses, that value is a Python `dict` / `list`.

This was chosen because it is the smallest implementation change from the original API layer:

| Benefit | Cost |
|---|---|
| Reuses the same value FastAPI can serialize as the response | Python object overhead can be larger than serialized JSON |
| Search filtering can run directly over cached lists/dicts | Cache maxsize counts entries, not bytes |
| No extra encode/decode step on each cache hit | Large broad indexes remain in process memory |
| No new service dependency | Cache is per Cloud Run instance, not shared |

This is acceptable for small/medium responses, but it is not necessarily the best representation for broad historical search indexes.

### Alternative cache/data representations

Consider these before increasing source-date limits or adding broad search to another data family:

| Option | What is cached/stored | Pros | Cons | Good fit |
|---|---|---|---|---|
| Python object cache (current) | `dict` / `list` in `TTLCache` | Simple, fast to filter, no new dependency | Higher memory overhead; entry-count bounded only; per instance | Small responses, short ranges |
| Serialized JSON bytes cache | UTF-8 JSON bytes/string | Lower and more predictable cache size than Python objects; easy byte accounting | Need decode for server-side filtering or return bytes directly | Cached final responses, not reusable indexes |
| Compressed serialized cache | gzip/zstd JSON bytes | Much smaller memory footprint | CPU cost; filtering requires decompression and parsing | Large full responses served as-is |
| Pre-published compact R2 artifact | `market_info` writes compact monthly/yearly indexes to R2 | Moves heavy build work out of Cloud Run; shared across instances; predictable R2 storage | Requires publish contract and freshness/version metadata | Broad search used repeatedly |
| External shared cache (Redis/Memorystore) | Serialized values outside process | Shared across instances; can enforce memory policies | New paid/operational dependency; may affect free-tier goal | High traffic after proving process cache is insufficient |
| Query result cache | Only filtered result rows | Very small for selective queries | Low reuse across many query variants | Repeated exact searches |

Preferred direction:

- Keep Python object cache for small manifests, day objects, short `/range`, and moderate `/search`.
- For broad historical search or data families whose compact index is large, prefer a compact R2 artifact published by `market_info` before adding more Cloud Run memory cache.
- Use serialized/byte-bounded cache only when the response can be returned as-is or the implementation explicitly accounts for decode/filter cost.
